# 分析执行、检查点与恢复

本页细化已批准的 PIPELINE，保留 core 1.0 类型与 CLI 命令契约；内部模块和状态可以演进。当前实现进度以 CLI capabilities 和测试为准。

## 本轮实现范围

当前打通 `import → analyze → inbox → feedback/resolve/mark-read`，含 HTML 输出、SQLite 检查点、同步 Jev/LLM 客户端和离线 Mock。本轮 `ours` 先提供基本闭环：控制器按规则选择动作；小积压直接抽取，其余按时间与回复形成 burst，由规则或 Decider 归属话题。

完整策略仍有缺口：MergeTopics、控制器用 Jev 选择动作、embedding 候选排序、模糊归属的 LLM 复核、跨 burst 的 @ 关系、纯占位刷屏压缩及相关阈值调优尚未接入。配置文件保留对应预定参数，不代表全部已生效。`stats/decisions/jev-log` 查询命令、GUI、指标评估也尚未提供；运行中的 decision/stats 事件和内部决策日志已经存在。不能把本轮 Mock 通过视为真实聊天分类质量验证。

## 执行阶段

| 阶段 | 行为 | 失败或退出后 |
|---|---|---|
| 只读计划 | 固定 chat、时间窗口、消息 ID 与话题快照；只读 dry-run 在此结束 | 不创建数据库、不改 failed、不写缓存或运行日志 |
| 取得会话锁 | engine 持有按数据库与 chat 隔离的操作系统文件锁；检查数据库版本，登记 run | 同 chat 第二个进程退出 7；进程退出会释放锁，遗留 running 记录在取得锁后标 cancelled |
| 分配话题 | 小积压可直接抽取话题；其余按 burst、回复规则和 Decider 分配，持久化 pending 归属 | 归属与分析完成分开；没有通过校验的消息仍待处理 |
| 抽取 | LLM 只提出条目与证据，使用本次短引用映射；保留 topic 的待校验工作单元 | 不修改分析完成状态；已缓存响应可供重试复用 |
| 待校验 | 即使 items 为空也保留这个阶段，不以草稿条目数量代替工作单元数量 | Verify 仍执行一次，空结果也能形成完成检查点 |
| 校验并提交 | 时间规则、证据匹配、规则 @我、排序；一个话题的结论/证据/消息状态/检查点在同一事务提交 | 提交失败全部回滚；提交成功后才输出 insight 事件 |
| 结束 | 所有阶段受 max_steps、请求超时、有限次重试、取消和预估预算约束 | 话题级失败、预算/步数耗尽则 partial；全局认证/配置/存储错误按错误码退出，已有提交则保留并报告 partial；重跑处理 failed/pending |

不声称旧四元组证明成立。有限 max_steps 加上每次请求的有限总超时给出本次执行的上界；取消在请求之间检查，不把进程强杀包装成正常完成。

## 数据边界

- 网络请求期间不持有 SQLite 写事务。只有 engine::store 打开数据库；会话锁文件放 `<data-dir>/tmp/engine/`，不在运行时删除锁文件，避免另一个进程锁到不同 inode/文件对象。
- 同一运行只推进快照内、时间范围内的消息。上下文消息不因此改变状态；期间新导入的消息留给下一次。
- 每次提交重新检查消息是否撤回。撤回不能继续提供有效证据；已保存结论在读取收件箱时也核对当前证据。
- `last_analyzed` 可包含 failed；`view_cursor` 只能到连续 done/skipped 前缀。查询和分析都不推进 `last_reviewed`。
- 模型不得选择任意数据库 ID：message 引用必须属于当前请求，update 必须命中传入的 open 结论；不存在或越界引用属于输出错误。
- 模型缓存键包含 provider/model、完整请求、提示词版本、渲染版本；缓存只在实际执行中写入。dry-run 不访问模型。
- Direct 的每个话题草稿在保存归属前缓存；同一输入恢复为 dirty topic 时可继续 Verify。普通话题抽取也保存待校验草稿。上下文、用户身份或模型设置变化后重新计算缓存键；进程在服务端响应到本地持久化之间崩溃，仍可能重新请求，不能承诺绝不重复计费。
- open 结论更新时保留 ID 和 lifecycle，并去重追加旧证据；旧证据的当前源消息一并参与重验。回填不会让话题最后活动时间倒退。
- 预算是按配置单价得到的本地估算，不是服务端账单硬限制；请求前按输入文本与输出上限保守预留，并为有限重试预留空间。已知 token 用量与费用分别记录。
- Jev 请求在客户端完成有限重试后仍失败，余下决策改用 LLM，单次运行只发一次 `W_DECIDER_FALLBACK`。缓存命中也留下本轮答案记录。分类请求按最多 40 条消息分批，避免一条超大话题生成无限增长的问题集合。

## 模块与性能

- `agent/mod.rs` 维护执行阶段和检查点边界；`agent/runtime.rs` 管理模型请求、缓存与预算；`segment.rs` 只计算消息组与回复交错率。SQL 仍集中在 `store`，确定性算法不打开数据库或发网络请求。
- 话题提交与提交后证据事件只按去重后的证据消息 ID 查询当前来源，复用准备好的 SQL 语句和 `message_id` 唯一索引；不再为每个话题扫描、反序列化整段聊天历史。读取仍在单事务中完成，撤回与跨会话验证不变。
- 抽取后的多条证据共享按消息 ID 建立的借用索引，不为每次校验或排名线性查找并复制正文。性能结论以算法访问量及查询计划为依据，未给出未经基准测量的墙钟提速比例。

## 用户状态

resolve 只设置 lifecycle；feedback 只替换当前有效评价。相同值重复调用不改变状态。偏好权重从当前有效评价重算，旧评价替换后不再贡献；排序调整限制在 ±0.5，不能改变 P0–P3 层级。

## 验收重点

用 Mock 验证零条目成功、坏引用、虚构证据、抽取/校验重试、话题提交失败、部分成功后续跑、快照外新消息、撤回、预算/步数上限、同 chat 并发、空/非空已读边界；模型 HTTP 协议另用本地假服务器，不调用付费服务。
