# GUI 设计复核问题清单

## 复核范围与标记

本清单依据 `apps/gui/README.md`、`docs/tasks/task-B-gui.md`、`docs/CLI_PROTOCOL.md`、当前 `apps/gui/src/ui*.rs` / `appearance.rs` / `app.rs`，以及 `docs/verification/gui/` 中的合成数据截图整理。现有截图主要覆盖收件箱宽屏、窄屏、深色和裁切状态；运行统计、决策日志和分析总览的条目主要来自源码静态复核，仍需用合成数据做原生界面验收。

这是一份修改前清单；下面的“本轮结果”在实现和合成截图验收后补充，避免把静态观察误当成已验证行为。

- **P0**：会误导操作、阻断主要流程，或让安全边界难以理解。
- **P1**：直接影响主要界面的可读性、稳定感和最终演示效果。
- **P2**：不阻断流程，但值得在后续继续打磨。

## 本轮结果

已优先处理 P0 与主要 P1：

- 1/2/3：导入文案、选择器与 CLI 忙碌态分离；阅读进度按栏统计，按钮禁用原因和页码范围可见，分页滚动区使用栏/页独立 ID。
- 4：错误条增加“操作未完成”标题、“检查设置”和关闭动作；部分失败保留 CLI 的具体结果，自动刷新群列表/收件箱不清理错误，主动重试分析/导入或关闭提示后清理。
- 5/6/7/8：窄窗口改用群组选择器；一级导航、主操作、运行详情分层；卡片与证据使用容器；中文日期、数量和状态文案统一。
- 9：`noto-sc` 置于比例与等宽字体族首位。
- 10/11：空状态、证据核验/引用、高亮和证据折叠状态分别说明原因；高亮按 Unicode 标量边界处理。
- 12/13/14/15：新增结构化运行统计、决策日志和分析总览，补齐 KPI、方法/概率、页签计数、负责人、截止状态和引用入口。

这些结果已用固定 `--demo` 合成数据跑通 GUI 单元测试，并在本目录的五张主截图与窄窗口截图中复核。P2 的即时写操作回执和设置路径向导仍留作后续工作。

PR #7 后续复核修正了错误提示被自动刷新清掉、累计统计被旧运行遮住和演示优先级三处回归。P1 示例采用无截止日期的进展通知，P2 为他人负责且无截止日期的待办，P3 为闲聊摘要；带截止时间的报告仍为 P0。截图由修正后的合成数据重新生成。

## P0

### 1. 文件选择状态和导入范围会误导

- **哪里**：顶部“导入 JSON”按钮、系统文件选择器打开期间的工具栏状态。
- **现象**：按钮文案容易让人理解为支持任意 JSON，但协议只支持已经写完并关闭的单文件 QCE JSON，不支持 chunked-JSONL。源码还把 `picking_file` 与 CLI 忙碌合并为同一个 `busy` 状态；选择器打开时会出现“停止”，但该按钮只会取消 CLI 子进程，不能关闭系统文件选择器。
- **建议**：按钮改为“导入 QCE 文件”，旁边或空状态中说明“仅支持单文件 `.json`，不支持 manifest/chunks”；把“正在选择文件”和“CLI 正在运行”拆成两个状态，选择器打开时显示“等待选择文件…”，不要提供无效的“停止”。
- **本轮计划**：是。

### 2. 已读边界正确但用户难以完成

- **哪里**：顶部“标为已读”、收件箱“还有 N 项尚未完整显示”提示、三栏/标签页的阅读覆盖状态。
- **现象**：当前安全规则要求每个结论在对应栏、页面和滚动区域中完整显示后才允许标读，这个边界不应放宽；但界面只给出总剩余数，没有指出还需查看哪个栏、哪一页，也没有解释按钮具体为何禁用。刷新快照后阅读覆盖会重新计算，界面也缺少明显提示，用户容易把禁用态误判为功能失效。
- **建议**：保留现有严格授权规则，同时在按钮 tooltip 或就近状态条中说明禁用原因；按栏显示“已查看 X/Y”，对仍未查看的标签和页面加提示；新快照到达时明确提示需要重新浏览。总览继续明确标注“只读，不计为已读”。
- **本轮计划**：是。

### 3. 分页与滚动位置可能让内容被跳过

- **哪里**：收件箱每栏分页、每栏独立滚动区，以及总览的外层分页和结论组内分页。
- **现象**：收件箱滚动区 ID 只含栏编号，不含页码，切换“上一页/下一页”时没有显式回到页首，新页面可能沿用旧页面的滚动位置。它与“必须完整显示才可标读”的规则叠加后，用户更难判断遗漏位置。总览同时存在外层每 20 项分页和组内“上一组/下一组结论”，形成两级分页，层级不够直观。
- **建议**：切页后强制滚动到页首并把焦点移到页标题；滚动状态按栏和页分别保存，显示“第 A–B 项 / 共 N 项”；总览尽量只保留一级主分页，必须嵌套时把组内分页做成清晰的局部控件并标注所属话题。
- **本轮计划**：是。

### 4. 错误提示缺少上下文和恢复动作

- **哪里**：顶部工具栏下方的全局 `last_error` 文本，以及导入、分析、刷新、总览、写操作失败后的反馈。
- **现象**：所有失败目前主要压成一行红色文本，可能直接暴露 `E_*` 代码或协议细节；长错误会挤压顶部区域，且用户不易判断失败的是哪次操作、是否可重试、部分分析结果是否已经保存。旧错误与当前页面的关系也不清楚。
- **建议**：使用带标题的就近错误条，按“操作 + 人话原因 + 结果影响”组织内容；为可恢复错误提供“重试”，为配置错误提供“打开设置”，并把错误码和完整技术信息折叠到“详情/复制诊断”。`partial` 要明确说明已保存部分与未完成部分，不能显示成完整成功。
- **本轮计划**：是。

### 5. 窄窗口仍依赖固定左栏和完整工具栏

- **哪里**：800 px 窄窗口截图中的群列表、顶部工具栏、P0/P1/P2+P3 标签和结论卡片；更窄窗口的预期布局。
- **现象**：800 px 时左侧群列表仍占约 212 px，主要内容宽度明显收缩；顶部所有动作仍平铺，继续变窄后会多行换行并占用较多垂直空间。长群名、长标签、长错误和证据文本同时出现时，主要任务区会更拥挤。
- **建议**：增加窄屏断点：群列表可折叠为抽屉/下拉选择，次要动作收入“更多”，保留“分析/停止”和当前页面切换；标签显示数量但允许紧凑文案；为长标题、群名和错误设置合理换行与最大宽度。至少用合成数据覆盖 800×680，并补一个更窄尺寸的布局检查。
- **本轮计划**：是。

## P1

### 6. 顶部操作与页面导航层级混在一起

- **哪里**：应用标题后的“分析总览 / 收件箱 / 导入 / 分析 / 标为已读 / 刷新 / 设置 / 运行记录”。
- **现象**：页面导航、主要任务、危险/不可逆动作和设置入口都使用近似的按钮视觉重量。截图中禁用按钮较多时，用户第一眼难以分辨当前所在页面、当前群聊状态和下一步应该做什么。
- **建议**：把“收件箱 / 分析总览”做成稳定的一级导航；把“分析新消息”作为主按钮，“停止”只在真实 CLI 运行时替换主按钮；“刷新、设置、运行记录”降为次级动作。“标为已读”与阅读进度放在同一状态区，不与导入并列。
- **本轮计划**：是。

### 7. 三栏与结论卡片缺少明确容器

- **哪里**：宽屏三栏、栏标题、结论正文、证据、操作按钮之间的布局。
- **现象**：现有截图主要依赖分隔线和留白划分内容，结论卡片与栏背景接近；P1/P2 为空时大面积留白，而 P0 的标题、摘要、负责人、时间、证据和按钮连续排列，扫描重点不够突出。三个独立滚动区域也不容易被察觉。
- **建议**：为结论使用轻量卡片容器，固定“标题与状态—摘要—截止/负责人—证据—操作”的顺序；P0 的截止和逾期状态使用清晰 badge，避免所有截止日期一律呈错误色；栏头保持可见，并通过边界或滚动条提示每栏独立滚动。
- **本轮计划**：是。

### 8. 中文与数字混排不够统一

- **哪里**：截止时间、时区、更新时间、计数、分页、P0/P1 标签和证据发送时间。
- **现象**：界面同时出现“9月27日23:59之前”“09-26 10:00”“时区 +08:00”“P0  必须处理”“P2 / P3”等多套空格、日期和分隔符写法。中文、英文缩写和数字密集排列时，阅读节奏不稳定。
- **建议**：建立一套界面文案规则：中文日期统一为“9 月 27 日 23:59”，短时间统一为“09-26 10:00”，中英文/数字之间使用一致空格；去掉靠连续空格对齐的写法；统一使用“·”或明确的字段标签。协议原始 `deadline.raw` 可保留，但规范化时间应单独显示，不与原文混成一句。
- **本轮计划**：是。

### 9. 中文字体没有按规格置于字体族首位

- **哪里**：`apps/gui/src/appearance.rs` 的 proportional 和 monospace 字体族注册顺序。
- **现象**：任务规格要求打包中文字体位于两个字体族的首位；当前实现使用 `push("noto-sc")`，会把它追加到默认字体之后。中文虽然可作为 fallback 显示，但中英文混排可能分别命中不同字体，基线、字面大小和字重一致性没有得到规格要求的保证。
- **建议**：按规格将 `noto-sc` 插入 proportional 与 monospace 列表首位，并用合成的中文、拉丁字母、数字、emoji 和日志等宽场景核对；如果日志确实需要严格等宽拉丁字符，应另设明确的日志字体策略，而不是依赖偶然 fallback 顺序。
- **本轮计划**：是。

### 10. 空状态没有区分“没有数据”和“暂时没有结果”

- **哪里**：群列表为空、未选择群、所选群尚未分析、筛选后为空、单个 P0/P1/P2+P3 栏为空、总览单节为空。
- **现象**：当前多处使用“暂无事项”或“当前没有符合条件的内容。尚未分析的消息需要先运行分析”，但空数据也可能来自未导入、尚未选群、筛选条件、确实没有该优先级、窗口内无消息或存在待分析消息。统一文案会让用户误判原因。
- **建议**：为每种状态提供原因和唯一下一步：无群聊→“导入 QCE 文件”，未选群→“选择群聊”，未分析→“分析新消息”，筛选为空→“清除筛选”，某栏为空→说明该优先级当前为零，总览为空→同时展示窗口消息数与待分析数，避免把“零结果”表达成“分析成功且没有事项”。
- **本轮计划**：是。

### 11. 证据高亮的语义和失败状态不够醒目

- **哪里**：结论卡片中的“原文证据”、发送者/时间、高亮背景和核验失败提示。
- **现象**：现有截图中高亮主要依赖一块浅黄色/暗橄榄色背景，证据容器与正文边界较弱；高亮、文本选择和普通底色的区别不够明确。`highlight=null` 或 `ok=false` 时，用户需要读到末尾提示才知道没有可靠定位。长证据也缺少快速定位与复制入口。
- **建议**：把证据做成带左侧标记的引用块，使用兼顾浅色/深色的前景与背景组合；在发送者行直接显示“已核验 / 待核对”，无定位区间时明确写“未定位到逐字引用，以下为原文”；保留 Unicode 字符下标转换逻辑，不自行重新匹配 quote。可补“复制原文”作为次级动作。
- **本轮计划**：是。

### 12. 运行统计信息不完整且历史输出偏调试态

- **哪里**：底部“运行记录”面板中的本轮摘要、`history_stats` 输出和“统计”入口。
- **现象**：当前摘要只展示消息数、新增结论、费用和耗时，缺少话题新增/更新、验证/未验证/拒绝数量、调用和 token 结构；历史统计直接用 `Debug` 格式输出，字段命名和层级更像开发日志。费用也需要强调是本地估算而非账单。
- **建议**：将运行统计做成独立页签或结构化卡片：核心 KPI 一行，结论状态一组，模型用量按 stage/provider/model 表格展示；统一标注“估算费用”，对旧记录缺失数据展示“不可用”，不能当作 0。原始调试内容只放在可展开详情中。
- **本轮计划**：是。

### 13. 决策日志未满足规格中的表格信息量

- **哪里**：底部“运行记录”里的决策列表和“决策记录”历史查询。
- **现象**：当前每步只显示 step、`chosen` 的调试格式和 reason，和 stderr 日志、统计、模型回答混在同一滚动区；规格要求的候选动作、选中动作、method、概率/置信度和理由没有形成可比较的列。长理由或复杂动作会显著降低可读性。
- **建议**：为“决策日志”提供独立页签/表格，列出步骤、候选、选择、方法、概率/置信度和理由；动作使用中文摘要，保留原始 JSON 为折叠详情；支持按步骤展开，并在 rule、jev、fallback 之间使用文字 badge，而不是只靠颜色。
- **本轮计划**：是。

### 14. 分析总览缺少总览感和各节状态提示

- **哪里**：“分析总览”的时间窗口、六个节标签、元数据、列表行和空结果。
- **现象**：六个入口目前只有标签，没有数量和风险提示；窗口信息、待分析数与数据截止时间以两行弱文本呈现，容易被忽略。热门、优先、提及、截止和资料的行结构差异较大，但都用连续文本和分隔线展示；“待分析”“时间待确认”“窗口前仍未完成的 P0”等关键语义不够集中。现有验证材料尚未提供该页面的原生截图。
- **建议**：顶部先显示窗口、窗口消息、待分析和最后数据时间四个摘要；六个标签带数量。不同节使用稳定的卡片骨架，并显式显示“已分析/待分析”“已逾期/即将到期/时间待确认”“负责人”“窗口外延续事项”；资料入口固定提示只展示元数据、不读取正文。空节文案应引用当前窗口和待分析数。
- **本轮计划**：是。

### 15. 截止日期的危险色没有区分“有日期”和“已逾期”

- **哪里**：收件箱结论卡片的“时间：…”行及 P0 状态。
- **现象**：源码对所有截止时间都使用错误色，但规格只要求 P0 已过期时显示“已过期”。未来截止、仅原文时间和真正逾期使用同一危险色，会削弱告警含义；同时规范化日期被放在下一行弱文本里，用户不容易判断系统是否确认了日期。
- **建议**：普通未来截止使用中性强调色，临近截止使用警示色，确认逾期才使用危险色和“已逾期”badge；无法规范化时显示“时间待确认”，同时保留 `raw` 原文，不把猜测表现成确定日期。
- **本轮计划**：是。

## P2

### 16. 筛选和写操作缺少即时结果反馈

- **哪里**：“包含已读 / 包含已处理”、有用/不重要、完成/忽略/恢复等控件。
- **现象**：筛选是复选框，写操作完成后主要依赖刷新后的内容变化；在网络/CLI 延迟或 `changed=false` 时，用户不容易确认请求是否提交、是否已经是目标状态。按钮禁用也普遍没有原因说明。
- **建议**：写操作期间仅锁定对应卡片并显示进行中，完成后短暂显示“已完成 / 无需更改”；筛选区显示当前结果数量和“清除筛选”；所有因 capability、demo、未选群或忙碌而禁用的关键按钮提供简短 tooltip。
- **本轮计划**：否，先完成 P0/P1 主界面打磨。

### 17. 设置窗口对路径错误的预防不足

- **哪里**：“设置”窗口中的 CLI、数据目录和配置文件路径输入。
- **现象**：三个路径均为自由文本，只有保存时统一重新连接；界面没有显示路径类型、是否存在、默认值来源或保存后的实际解析路径。对完全不熟悉项目的用户，CLI 路径和数据目录容易填反。
- **建议**：增加“选择文件 / 选择文件夹”按钮和字段说明，保存前做非阻塞校验；连接成功后显示 CLI 版本、协议版本和实际数据目录。高级配置路径可默认折叠。
- **本轮计划**：否，作为后续易用性改进。
