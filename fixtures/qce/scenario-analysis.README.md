# 多场景合成分析样本

这组文件用于离线导入回归、受控 Mock 分析和后续人工模型评估。全部人物、QQ 标识、聊天文字、活动和附件均为手写虚构数据，没有读取真实群聊、账号、密钥或网络。附件只有元数据，不包含文件、图片或音视频内容。

- `scenario-analysis.json`：100 条顶层消息，6 名虚构成员，另有 1 条系统消息；其中两人的显示名都是「合成林舟」，但 UID/UIN 不同。
- `scenario-analysis-backfill.json`：3 条新增历史消息，以及主文件第 19 条的完整原样重复。顺序导入两个文件后共有 **103 条唯一顶层消息**。
- 主文件第 70 条另外包含 2 条转发内部消息，不计入上述顶层消息数，不是独立导入记录。

结构沿用 [Docker 导出模板](template-docker-export.json) 和 [上游字段核对](../../docs/QCE_DOCKER_EXPORT.md)，对应文档已核对的上游 commit `7fcca88880c2eb8c12c51c2b6cc49ee805a53d0c`。未复制上游实现，未添加 `scenario`、标准答案、话题 ID、优先级、关闭时间等自创生产字段。`metadata.version` 的 `0.1.0` 沿用模板，不表示对当前 Docker 镜像版本作了新验收。

| 我的 UID / UIN | `u_scenario_self` / `290000001` |
| 我的名字 | 合成林舟 |
| 另一位同名成员 | `u_scenario_same_name` / `290000006` |
| 其余成员 | 合成陈禾 `u_scenario_chen` / `290000002`；合成王砚 `u_scenario_wang` / `290000003`；合成赵晴 `u_scenario_zhao` / `290000004`；合成苏棠 `u_scenario_su` / `290000005` |
| 分析时区 | `+08:00`，不随执行电脑时区变化 |
| 人工评估固定 now | `2026-09-26T20:00:00+08:00` |
| 主文件发送时间 | `2026-09-24T09:00:00+08:00` 至 `2026-09-26T09:09:00+08:00` |

固定 now 是评估口径，不是 JSON 字段，也没有在这里承诺 CLI 支持 `--now`。需要固定展示窗口时应在测试接口中提供该时间；普通 CLI 使用实际运行时间。相对日期必须以对应证据消息的 `sent_at` 为锚点，不以 fixed now、导入时间或电脑时间计算。

顶层 `timestamp` 和转发内部 `timestamp` 均为毫秒；可读 `time` 为同一时刻的 UTC RFC 3339。reply 元素内部 `timestamp` 按上游结构为秒，不能混用。

以下表格中的编号 N 对应源消息 ID `9200000000000000000 + N`，以十进制字符串保存；例如 1 是 `9200000000000000001`，100 是 `9200000000000000100`。这不是 engine 内部的 `m_...` ID；不得把源 ID 当作模型的短引用或已验证证据 ID。

## 分段、关闭和回填的执行顺序

1. 使用独立测试 data-dir，配置 `timezone = "+08:00"`。先只导入主文件并分析；不要把回填文件同时导入后才开始分析，否则就没有「已关闭后补入历史」这一时序。
2. 分段实验可将 `[agent]` 中的 `direct_max = 0`、`segment_batch = 10` 作为测试配置，保留默认 `[segment].topic_close_secs = 21600`。这样 41–50 与 87、1 与 91 的 reply 必然跨处理批次；默认 300 条批量下，本样本本身不保证跨 Segment 调用。
3. 为单独观察合并，可先只分析 9 月 24 日 11:00–11:20 的半开窗口，在之后 16:00 的消息关闭旧话题之前检查名单候选。若模型已经把签到表和报名页正确分在同一话题，零合并也是合理结果；若分成两个已处理 Active 话题，才检查有效跨话题回复数、Decider 确认及原子合并。全文件一次完成不保证在关闭前触发合并。
4. 对关闭与回填，先完成主文件分析，记录包含 18–20 的话题状态、成员、`last_message_at`、首次关闭边界和已有结论状态，再导入回填文件。新历史消息为 9 月 24 日 12:15、12:16、12:17，早于 16:00 之后的处理边界，且距 09:19 不到六小时。
5. 若 18–20 原本独立归入同一话题且已 Closed，新历史回复应可参加历史归属，成功后保持 Closed；最后活动时间只取最大值，首次关闭边界不移动。已读位置、用户 resolve/反馈状态不能因回填被重置。该检查依赖实际话题结果，不能仅凭导入成功判定通过。
6. 重新导入两文件，检查重复消息不新增。任何用 Mock 证明的行为都应标为 Mock；调用真实云模型进行全场景质量评估须单独记录模型、配置、响应、花费和人工结论。

`since` 包含下界，`until` 不含上界。例如第一组 6 条消息的精确窗口是 `[2026-09-24T09:00:00+08:00, 2026-09-24T09:06:00+08:00)`，不是到 09:05 为止。

仅导入和查看只读分析计划的本地示例：

```powershell
cargo run -p chat-tldr -- --data-dir ./private/scenario-analysis config init
cargo run -p chat-tldr -- --data-dir ./private/scenario-analysis import ./fixtures/qce/scenario-analysis.json
cargo run -p chat-tldr -- --data-dir ./private/scenario-analysis analyze --chat qq:group:synthetic-analysis-group --dry-run
```

省略 `--dry-run` 才会进入已配置模型的实际分析。本说明没有运行该云端步骤，也没有把固定 now 或额外评估标签塞进生产请求。完整执行边界见 [ANALYSIS_EXECUTION](../../docs/ANALYSIS_EXECUTION.md)。
